Khi AI Học Đọc Codebase:
Kiến Trúc Đằng Sau Trợ Lý Kỹ Thuật Thế Hệ Mới

01/10/2026 · AI Engineering · Fastdo Internal Research

Hầu hết AI assistant chỉ biết hỏi rồi trả lời. Nhưng thứ đang được xây tại Fastdo khác — nó phải hiểu đồng thời cả vấn đề nghiệp vụ của khách hàng và đoạn code nào trong hệ thống đang xử lý nghiệp vụ đó. Bài này phân tích kiến trúc hai pipeline và triết lý evidence-based reasoning đằng sau dự án AI Ticket Agent.

// VẤN ĐỀ CỐT LÕI: TẠI SAO RAG ĐƠN THUẦN KHÔNG ĐỦ?

⚡

Nhét cả codebase vào RAG — nghe hợp lý, nhưng không ổn

Cách làm phổ biến nhất khi muốn AI "hiểu code" là nhét toàn bộ source code vào RAG (Retrieval-Augmented Generation — kỹ thuật cho AI truy xuất tài liệu liên quan trước khi trả lời). Vấn đề: một codebase production thật có hàng nghìn file, hàng trăm class — AI không phân biệt được đâu là code liên quan đến ticket, đâu là code không liên quan. Nó retrieve theo từ khóa, không theo logic nghiệp vụ.

🎯

Giải pháp: tách làm hai lớp tri thức

Thay vì nhét raw source code, dự án xây hai pipeline độc lập sinh ra tri thức có cấu trúc — rồi mới đưa vào RAG. AI Ticket Agent chỉ đọc knowledge, không đọc code trực tiếp.

Roslyn — không phải grep, mà là hiểu cấu trúc

Roslyn là compiler platform của Microsoft cho C#/.NET — nó không chỉ tìm text, mà thực sự parse và hiểu cú pháp. Dùng Roslyn, tool có thể biết chính xác: method A gọi method B ở dòng nào, entity nào bị read hay write, endpoint HTTP nào map với controller nào. Kết quả là một graph quan hệ: Controller → Service → Repository → Entity.

// Output không phải keyword matching, mà là graph quan hệ có evidence: TimekeepingController.GetSummary() → calls TimekeepingService.BuildSummaryAsync() → calls TimesheetRepository.GetByRangeAsync() → reads Entity: TimesheetEntry → evidence: file=TimekeepingController.cs:L142, hash=a3f9c2...

// TRIẾT LÝ: AI KHÔNG ĐƯỢC NÓI CHẮC HƠN BẰNG CHỨNG

Đây là điểm khác biệt quan trọng nhất — và cũng là điều ít hệ thống AI thực sự làm đúng.

// QUY TẮC EVIDENCE

Loại Khi nào dùng Ví dụ
FACT Có file + line + content làm bằng chứng "Service X gọi Repository Y tại dòng 142"
HYPOTHESIS Logic hợp lý nhưng chưa trace đủ "Có thể lỗi xuất phát từ điều kiện A"
UNKNOWN Không đủ dữ liệu "Không tìm thấy caller — có thể gọi qua reflection"
🚫

Vì sao "không thấy caller ≠ dead code"?

Static analysis chỉ thấy những gì viết trực tiếp trong source. Nhưng trong .NET, method vẫn có thể được gọi qua Reflection, Dependency Injection, Framework convention, hoặc code ngoài solution. Gọi đó là "dead code" chỉ vì Roslyn không thấy caller — là overclaiming. Tool đánh dấu unreferenced_candidate, không phải dead code.

// STALE KNOWLEDGE & SECRET SAFETY

🔄

Knowledge có hạn sử dụng

Code thay đổi theo commit. Mỗi knowledge chunk lưu content hash — khi source file thay đổi, hash mới khác hash cũ, chunk được đánh dấu stale. AI không được dùng knowledge stale như sự thật hiện tại. Cơ chế này tránh tình huống AI tự tin tư vấn dựa trên code đã bị refactor từ 3 tháng trước.

🔐

P0: Secret không được lên RAG

Codebase thực tế có thể chứa connection string, MongoDB URI, API key cứng trong config. Pipeline phải phát hiện → redact → scan lại output trước khi cho phép tạo package upload. Không có step này, một RAG query vô tình có thể trả về credential thật.

// TẠI SAO CÁCH NÀY KHÓ VÀ ĐÁNG ĐỂ LÀM?

Xây chatbot AI hỏi-đáp thì dễ. Nhưng xây một agent hiểu đồng thời nghiệp vụ và implementation, phân biệt fact với hypothesis, tự phát hiện khi knowledge của mình đã cũ, và không rò secret — đó là bài toán khác hẳn. Khi thành công, developer không cần đọc cả solution để hiểu một ticket. AI làm việc đó trước — và nó nói rõ mình chắc đến đâu.
